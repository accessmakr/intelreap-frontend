02 Two Questions, One Name

Search results for "reverse IP lookup" mix two different questions, and the difference decides which tool you need.

The first is a reverse DNS lookup. You ask the DNS what hostname was set for an address, and it answers with a PTR record. DNS answers it directly, so no separate dataset is involved. The second is the domain list: which websites resolve to this address. No DNS query can answer that, because DNS only maps a name to an address, not an address to every name pointing at it. Providers answer it from a dataset they build themselves. The two are often both called reverse IP lookup, which is why a hostname tool and a domain list tool can give very different results for the same address.

03 How the Hostname Is Found, With Commands

A PTR record is stored under a name made from the address written backwards. For IPv4 the four numbers are reversed and in-addr.arpa is added; Microsoft's DNS documentation describes the same reversal. For IPv6, RFC 3596 defines the domain as ip6.arpa and writes the address as single hex digits, separated by dots, again in reverse order.

You can run the same lookup from a terminal. These are standard tools on each system, and the address below is the one the tool above uses as its example.

Commands for a PTR lookup
ToolCommandSystems
nslookupnslookup 8.8.4.4Windows, macOS, Linux
digdig -x 8.8.4.4 +shortmacOS, Linux
hosthost 8.8.4.4macOS, Linux

An address can have more than one PTR record, because DNS allows several records with the same name and type (RFC 2181 calls such a group a Resource Record Set). The tool lists every PTR hostname it receives, up to five. Who sets the record is a matter of delegation: it is normally managed by whoever manages the address block, usually the hosting provider or ISP, not by the owner of a website on that address.

04 Forward-Confirmed Reverse DNS

A PTR record is just a claim, because the party that controls the reverse zone can name any host. A stronger check closes the loop: look up the PTR hostname, then look up that hostname's A or AAAA record, and see whether it gives back the original address.

RFC 1912 recommends that every address have a matching PTR record and that PTR and A records agree; it is an Informational RFC, so this is guidance, not a requirement. The rule that gives the loop real weight is email. Google's sender guidelines say a sending server's public IP must have a PTR record that resolves to a hostname, and that the hostname must have an A or AAAA record resolving to the same IP. That is why mail administrators care, and why the tool reports whether the loop closes.

05 Why Many Domains Share One IP Address

An address does not need one website. When a browser opens a page it sends the domain it wants in the HTTP Host header, and in HTTPS it also sends the name in the TLS handshake as the server name indication. RFC 6066 describes the second as a way to reach servers that host multiple virtual servers at a single network address. The server reads the name and serves the matching site.

This is why a list of domains on an IP is possible, and also why it is not a list of one owner's sites. Many unrelated customers can sit on one shared server. For the busiest addresses, such as those used by large content delivery networks, the number of domains is so large that DomainTools says its reverse IP API returns only a subset and that full enumeration is not possible with it.

06 Where Domain Lists Come From and What They Miss

No registry holds a list of every name pointing at an address. Providers build their own datasets by resolving large numbers of domains and recording which address each one returned, then answer lookups from that data. DomainTools, for example, describes its Iris dataset as tracking the actively resolved addresses of apex domains and as updated daily.

Because the answer comes from a dataset, its quality depends on that dataset. A domain added after the last crawl will not appear, a site that moved can linger against its old address until it is resolved again, and a busy shared address returns only part of its domains. This page does not list domains on an address, because that needs a data source IntelReap does not use. Where a result matters, compare more than one provider.

07 What Reverse Lookups Are Used For

Mail delivery. Administrators check that a sending address has a PTR record that matches its hostname, since receivers such as Gmail look for it.

Investigations. Security researchers look at which names share an address with a suspicious site. It is a lead, not a conclusion, because shared hosting puts unrelated customers together.

Hosting checks. Site owners on shared hosting see which other domains share their address, which matters most for email, where Google notes that the activity of any sender on a shared IP affects the reputation of every sender using it. To see whether your own connection sits in a hosting or VPN range, the VPN and Proxy panel flags it.

Related-site research. Marketers sometimes use a domain list to find other sites on the same address. A shared address is a weak signal of common ownership, so it should be confirmed another way.

08 What a Reverse Lookup Cannot Tell You

A hostname does not identify a person or a website's owner. On shared hosting, the domains on an address often belong to unrelated parties. A PTR name is set by whoever manages the address block, so it may be generic or generated and say nothing about who uses the address. A domain list is only as complete and current as its dataset. And neither shows what a device is doing: an address can be shared by many users, or change hands, so recognising a visitor takes more than the IP, as device fingerprinting shows.

Logic

Separate the two questions first, because one is a live DNS query and the other depends on a dataset. Show the live one as a working tool, explain how the reverse name is built, then explain why a domain list is a snapshot and what it misses.

Methodology

The tool runs in your browser: it builds the reverse name, sends PTR and A or AAAA queries to public DNS resolvers over HTTPS in their JSON format, and compares the results. It stores nothing and sends nothing to IntelReap. That JSON format has no RFC, so behaviour can differ between resolvers; if one fails the tool tries another. The reverse-name rules follow RFC 1035 (confirmed through Microsoft's DNS documentation, not by reading the RFC text itself) and RFC 3596. The Host header explanation rests on RFC 9110 as quoted in IETF documents, and the point about who manages a PTR record is general DNS delegation practice, not separately sourced. Statements about how datasets go stale follow from how snapshot data works and are not quoted from a provider. The terminal commands are standard tools and have not been run on a real machine for this page. We do not provide a domain list.

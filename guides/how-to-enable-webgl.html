Quick Answer

WebGL is on by default, so fix what blocks it

WebGL is on by default, so a failure usually means graphics acceleration is off, the GPU is blocklisted, or a driver is outdated. Run the check below, then follow the steps for your browser. WebGPU errors such as "found no usable graphics adapter" have the same causes.

02 Why WebGL Fails

WebGL is on by default in current browsers, so a failure almost always comes from something that sits between the page and the GPU. The browser checks a blocklist of graphics drivers it does not trust, then needs graphics acceleration turned on, then needs a working driver that can reach a GPU.

Each step has its own fix. A blocklisted driver is fixed by updating the driver or, as a last resort, overriding the list. A setting that is off is fixed in the browser. A missing or outdated driver is fixed by installing one from the maker. A remote desktop or virtual machine often has no GPU to reach, which we treat as general practice, not a sourced rule.

If you are not sure what a GPU does, What Is a GPU? explains it.

For problems beyond the browser, such as a failing card, see the GPU troubleshooting guide.

03 Chrome and Edge

Chrome and Edge share the same engine and the same fixes.

  1. Open Settings, then System, and turn on Use graphics acceleration when available. Older versions call it Use hardware acceleration when available. Relaunch the browser.
  2. Open chrome://gpu (edge://gpu in Edge) and read the WebGL line. Hardware accelerated is what you want. Software only means the browser fell back to the CPU, and the Problems Detected list explains why.
  3. If the GPU is blocklisted, open chrome://flags/#ignore-gpu-blocklist and set Override software rendering list to Enabled, then relaunch. Use it to test, not as a permanent fix.
  4. Update the GPU driver from NVIDIA, AMD or Intel, or through your computer maker.

The Edge addresses follow the same pattern but are not documented by Microsoft in the sources we checked.

04 Firefox

Firefox has its own blocklist and its own preferences.

  1. Open Settings, General, Performance. Clear Use recommended performance settings to reveal Use hardware acceleration when available, and make sure it is ticked. Newer versions may place this under Tabs and browsing. Restart Firefox.
  2. Type about:config, accept the warning and search for webgl.disabled. It should be false.
  3. Open about:support and read the Graphics table. The WebGL 1 and WebGL 2 driver renderer lines should name your GPU, and a blocked driver says so.
  4. As a last resort, set webgl.force-enabled to true.

Mozilla's wiki says to force-enable a blocked feature at your own risk, and that if forcing it does not work your hardware probably does not support it. A Mozilla bug thread from Firefox 68 says only WebGL 1 could be forced then, so it may not help with WebGL 2.

If Firefox crashes or draws wrongly, Mozilla's guidance is to update your graphics driver and, if that fails, to turn off hardware acceleration and then WebGL (set webgl.disabled to true).

05 Safari

WebGL is on by default in current Safari. A vendor help page says WebGL is enabled by default from Safari 15.1, and that the only way to turn it on or off is the terminal. Older Safari versions had a WebGL 2.0 switch under Develop, Experimental Features. Newer macOS versions show Feature Flags in Settings, Advanced, after you tick Show features for web developers. If WebGL fails in Safari, update macOS or iOS and Safari first, because settings are rarely the cause.

These Safari details come from support pages of other companies, not from Apple, so treat them as the weakest part of this guide.

06 "Found No Usable Graphics Adapter" (WebGPU)

Many web apps and games show a message such as "found no usable graphics adapter" when WebGPU cannot get a GPU. It is a WebGPU message, not a WebGL one, but the causes overlap.

Chrome's own WebGPU troubleshooting page lists the reasons, in this order:

  1. Graphics acceleration is off in chrome://settings/system.
  2. The platform is not supported. WebGPU needs Chrome 113 or later on ChromeOS, macOS and Windows, Chrome 121 or later on Android, and a secure (https) page.
  3. The GPU is blocklisted. chrome://gpu then says WebGPU has been disabled via blocklist or the command line, and the chrome://flags/#ignore-gpu-blocklist and chrome://flags/#enable-unsafe-webgpu flags can override it for testing.
  4. No adapter matches the options the app asked for.
  5. There is no GPU, hardware or software-emulated. chrome://gpu should read WebGPU: Hardware accelerated. If it reads Software only, update the GPU driver.
  6. The GPU process crashed several times. Reload the page or restart Chrome.

Mozilla shipped WebGPU on Windows in Firefox 141, and other platforms followed later or are still in progress, so an older or non-Windows Firefox may not have it. Firefox keeps its own blocklist, which the gfx.webgpu.ignore-blocklist preference overrides for testing.

07 "A WebGL Context Could Not Be Created"

This error means the browser tried to open WebGL and the graphics stack refused. Work through these in order and run the check after each:

  1. Turn on graphics acceleration in the browser.
  2. Update the GPU driver.
  3. Check whether the GPU is blocklisted: chrome://gpu in Chrome and Edge, about:support in Firefox.
  4. Try a different browser. Each browser keeps its own blocklist, so one can work where another fails.
  5. If you are in a remote desktop or virtual machine, it may have no GPU to give the browser.

09 How to Verify WebGL Is Working

Use any of these:

  1. The check at the top of this page, which also tells hardware from software.
  2. get.webgl.org, a test page that shows a spinning cube when WebGL works.
  3. The browser console: !!document.createElement('canvas').getContext('webgl') returns true when WebGL 1 opens, and the same with 'webgl2' tests WebGL 2.

The Capability panel lists WebGL beside the rest of what your browser reports.

Logic

Separate three things that look alike: WebGL missing, WebGL running in software, and a WebGPU error. Test them in the browser with the same contexts a web app uses, then send the reader to the one fix that matches, instead of one list of steps for everything.

Methodology

The check runs in your browser. It requests WebGL 2 and WebGL 1 contexts with and without the failIfMajorPerformanceCaveat setting, reads the renderer string through the debug renderer extension where the browser allows it, treats names such as SwiftShader, llvmpipe and Basic Render Driver as software, and asks WebGPU for an adapter. It stores and sends nothing. Browsers may hide the renderer, and a context that opens only without the fail-if-slow setting is reported as software. The Chrome and WebGPU causes follow Chrome's own troubleshooting page. Weaker, stated here: the Safari details come from other companies' support pages, the Edge addresses and the Firefox Performance menu location come from secondary guides, the Firefox about:support line names are from a secondary guide, the Firefox macOS WebGPU status is from a bug thread, and the remote desktop and virtual machine point is general practice. The get.webgl.org description comes from older guides and we did not open that page. We did not test the steps on real machines.
